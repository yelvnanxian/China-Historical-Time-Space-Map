## 来源取得与引文含义

新来源来自实际请求维基百科 MediaWiki API 后取得的完整公开条目文本，保存在 `data/evidence/historical-context/`。每个来源均保留页面 ID、修订号、修订时间、实际获取时间、API 地址、文本快照路径与 SHA256；应用中的百科链接使用 `oldid` 指向本次读取的固定修订，避免只链接不断更新的当前页面。

这些百科页面用于核对概述性时间节点，**不是逐条原始文献或考古论证**。数据没有将百科来源标为 `checked`。`evidence` 表示实际读到的原文摘录及其支持的窄事实；构建脚本和测试逐字检查摘录确实存在于快照。这种检查保证可追溯性，不等于确认页面内每一句话均正确。

历史地理主要来源为《黄河》《花园口决堤》《京杭大运河》《隋唐大运河》《都江堰》；城市节点采用各城市及《北京历史》《隋唐洛阳城遗址》《荆南》《扬州十日》等页面。内容选择避开了本次没有交叉核定的死伤总数和若干页面中明显存在分歧的年代，不把单一百科页面的全部叙述照搬进产品。

复用古籍为已有《资治通鉴》《旧唐书》相关卷的快照，来源元数据与原文保留在原证据目录。古籍引文保留原字形，现代说明与摘要使用简体。原始古籍年号、月份、干支日未擅自换算为某个公历日；`year` 用于跨条目排序，日期显示以 `dateLabel` 为准。

本次也尝试取得 UNESCO 世界遗产中心的大运河及都江堰官方页面，但服务器返回403，**没有把未取得的页面作为引用**。没有使用搜索结果摘要代替原文。百科与维基文库数字文本的出处、固定页面和相应许可信息随来源保留；本批中文概述为项目自行编写，引文按原文展示。本次还实际查询了维基百科站点许可 API，返回 CC BY-SA 4.0，记录保存在 `data/evidence/historical-context/license-check.json`。

## 坐标与空间关系

8 条地理信息的坐标全部逐字复制主 catalog 已有地区参考点，没有自行拟定新的决口经纬度。`referencePlaceId` 指明坐标从哪个已有地点取得：

- `event-area`：发生地区参考，例如用郑州市区入口介绍花园口工程、用滑州入口介绍1128年决河；不是决口现场的精确坐标。
- `affected-area`：影响或受益地区参考，例如成都点表示成都平原受益地区，都江堰工程本身不位于该坐标。
- `regional-reference`：相关区域的阅读入口，例如开封点连接兰考铜瓦厢事件，不能据此认定开封市区就是决口位置或受淹边界。

每条 `coordinateNote` 都明确该点表示什么、不表示什么。`affectedPlaceIds` 连接已有地区入口，不是精确洪泛区边界或逐城灾损清单。

本次**不提供古河道、古湖岸或水灾范围几何**。1128年至1855年的黄河南向摆动也没有被画成七百余年不变的一条线；现代自然河流底图继续承担现代地理参照作用。

## 构建与验证

```sh
python3 scripts/build-historical-context.py
npx tsx --test server/historical-context.test.ts
```

构建脚本只读取保存的文本与当前 catalog，逐条检查引文和引用，输出独立 JSON 及 `data/evidence/historical-context/validation.json`。重新构建不会更新原网页快照，也不会改主 catalog。

独立测试 **3 项通过**：

1. 来源快照存在、SHA256 一致、取得日期合法，百科固定到明确修订。
2. 地理条目关联已知地区，坐标与指定 catalog 地点一致，坐标角色明确，不含未经核验的河道线路。
3. 各城至少3个不同年份节点、按年升序、跨时期展示，来源和原文一致，关联事件及城市真实存在。

这些是数据完整性与可追溯性检查。它们没有把百科内容、传统建设年代或地区参考点当作已经完成学术考证的历史 GIS。
